> 记录范围：基于 `main@98e8233` 构建的未打包 Release 版本
>
> 试用产物：`target/release/gpui-pi.exe`
>
> 当前阶段：R17 正式安装包制作之前
>
> 本文仅记录试用中发现的问题，不代表已完成修复。

## 详细记录

### UI-001 左侧项目与会话区不支持按项目折叠

**现状**

左侧项目与会话区会直接展示项目下的全部会话，不支持以项目为单位折叠或展开。会话数量较多时，用户难以快速定位目标项目和目标会话。

**预期行为**

- 每个项目应作为独立分组展示。
- 项目分组支持折叠与展开其下全部会话。
- 折叠状态应有明确的视觉提示。
- 项目较多或会话较多时，用户仍能快速浏览和定位。

### UI-002 单个项目的会话列表没有展示数量限制

**现状**

单个项目下会直接展示全部会话，没有默认展示数量和独立滚动区域。会话过多时会占满左侧面板，影响其他项目、文件浏览器及底部入口的使用。

**预期行为**

- 单个项目默认展示最近的 **8 条会话**。
- 超出 8 条的剩余会话应在该项目的会话列表区域内滚动查看。
- 滚动会话列表时，不应挤压或带动左侧其他固定区域发生异常位移。
- 应保留当前会话的选中状态和可见性。

### UI-003 缺少启动全新会话的入口

**现状**

当前没有找到用于启动全新会话的明确按钮或入口，只能打开已有会话并在已有上下文中继续对话。

**预期行为**

- 提供清晰、易发现的“新建会话”入口。
- 新建会话不得继承已有会话的消息上下文。
- 新会话应绑定当前项目或允许用户明确选择目标项目。
- 创建成功后应自动切换至空白会话输入状态。

### UI-004 Tool CTA 展开时偶发滚动漂移

**现状**

在主会话面板点击 Tool CTA 展开详情时，消息区域有时会发生滚动位置漂移，导致被点击的 Tool CTA 离开原来的视口位置，影响连续阅读。

**预期行为**

- 点击某一条 Tool CTA 时，应将该条目锚定在当前对应的视口高度。
- 详情内容应主要从该条目当前位置向下展开。
- 展开或收起操作不应造成无意的整体滚动跳动。
- 如果下方空间不足，可以滚动补足可见区域，但不得改变用户正在关注条目的视觉锚点。

### UI-005 右侧会话导航不支持调整宽度和层级导航

**现状**

右侧会话导航面板宽度固定，不支持拖动调整；同时当前导航以扁平条目为主，没有实现与 pi-web 一致的会话内容层级导航。长标题或复杂会话结构下，可读性和定位效率较差。

**预期行为**

- 右侧会话导航面板支持拖动调整宽度。
- 应设置合理的最小宽度和最大宽度，避免挤压主会话区域或完全遮挡内容。
- 导航结构应参考 pi-web，实现相应的层级关系和视觉缩进。
- 父级、子级和当前定位项应具有明确的视觉区分。
- 调整宽度后，标题文本应正确换行或截断，不得出现布局溢出。

### UI-006 添加图片后输入框被压缩且内容无法滚动

**现状**

在会话输入框中添加图片后，图片预览会压缩文本输入区域；当输入内容超过剩余可见高度时，无法通过上下滚动查看已经输入的内容。

**预期行为**

- 图片附件区与文本输入区应合理分配空间，不应将文本输入区压缩至不可用状态。
- 文本输入内容超过可见高度后，输入区应支持垂直滚动。
- 光标移动、选择文本和输入新内容时，应自动保证当前光标位置可见。
- 图片较多时，附件预览区域自身应具备合理的尺寸上限或滚动能力。
- 添加或删除图片时，不应丢失已输入文本和当前编辑状态。

### UI-007 不支持通过 Ctrl+V 粘贴图片

**现状**

会话输入框不支持使用 `Ctrl+V` 将剪贴板中的图片直接添加为会话附件。

**预期行为**

- 当剪贴板中包含图片时，在会话输入框按下 `Ctrl+V` 应直接添加图片附件。
- 粘贴图片后应显示可识别的预览、文件类型或附件状态。
- 当剪贴板中是普通文本时，仍保持正常文本粘贴行为。
- 当剪贴板同时包含图片和文本等多种格式时，应采用明确且一致的优先级规则。
- 不支持的图片格式或读取失败时，应给出可理解的错误提示，不得静默失败。

### UI-008 含图片消息发送后临时显示原始图片数据

**现状**

发送包含图片的用户消息后，在助手回复生成期间，用户消息中的图片区域会被错误渲染为“未知内容 · image”，并直接展示图片消息的原始 JSON 结构和 Base64 数据。该异常仅在回复进行中出现；助手回复结束后，用户消息会恢复为正常的图片预览。

**影响**

- 原始 Base64 数据占用大量垂直空间，破坏当前会话的阅读位置和布局。
- 用户会误以为图片上传失败、消息内容损坏或出现乱码。
- 生成中状态与回复完成后的最终状态不一致，容易造成界面闪动和滚动位置变化。

**预期行为**

- 用户点击发送后，图片消息应从发送开始到回复结束始终使用稳定的图片预览组件。
- 流式回复期间不得将内部 JSON、Base64 数据或协议字段渲染到用户消息区域。
- 如果图片仍处于上传、解析或加载状态，应显示明确且尺寸稳定的占位状态。
- 图片处理失败时应显示可理解的失败提示，并允许重试或移除图片，不得回退为原始协议内容。
- 流式生成结束后不应通过替换整个用户消息节点来“恢复正常”，以避免额外的布局跳动或滚动漂移。

**复现步骤**

1. 在会话输入框中添加一张图片并输入文本。
2. 发送该条含图片的消息。
3. 在助手回复生成期间观察刚发送的用户消息。
4. 可看到图片区域临时显示“未知内容 · image”和原始 JSON/Base64 数据。
5. 等待助手回复结束后，该区域恢复为正常图片预览。

## 后续处理建议

1. 在进入 R17 正式打包前，先对上述问题进行产品与技术评估。
2. 将问题映射到独立修复轮次或明确的 backlog 项，避免直接在 `main` 上零散修改。
3. 修复 UI-004、UI-005、UI-006 和 UI-008 时增加窗口尺寸变化、长会话、长文本、多附件及流式回复场景的回归验证。
4. UI-008 应重点核对“发送后内存态消息”和“回复结束后持久化消息”是否使用了不同的内容解析或渲染路径。
5. 修复完成后重新构建 Release 版本进行一轮人工试用，再决定是否进入正式安装包制作。
