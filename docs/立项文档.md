## 一、项目定位与边界

用 GPUI + gpui-component 写一个 **pi 编程智能体的原生桌面客户端**，1:1 复刻 pi-web 0.8.9 的能力，不使用 Electron、不打包 Node/Python/DeepSeek Harness。

这是**新仓库、新项目**，不是 pi-web-desktop 的重写分支。两者并行存在、共用 `~/.pi/agent/`：

| | pi-web-desktop（保留） | GPUI-Pi（本项目） |
|---|---|---|
| 定位 | 兜底 + DeepSeek Harness 入口 + 扩展/技能部署 | 日常 pi 客户端 |
| 演进 | 冻结在 `claude/dsh-integration` 状态，不再加 pi 侧功能 | 主线 |
| 卸载条件 | GPUI-Pi 达到 1:1 且稳定运行 1 个月后再议 | — |

### 明确不做（v1）

| 不做 | 理由 |
|---|---|
| 内置 Python | 体积（340MB）；连带 `ppt-master`、`wiki-*`、`okf-visualizer` **全部移出 v1 范围** |
| 内置技能部署（`skills-seed`） | 技能住在 `~/.pi/agent/skills/`，由 pi-web-desktop 负责铺；GPUI-Pi 只消费不部署 |
| DeepSeek Harness 第二运行时 | 留在 pi-web-desktop |
| Mermaid 渲染 | 源码直出为代码块。**连带收益：不需要 WebView，不依赖 WebView2 Runtime** |
| PWA / 移动端布局 / 浏览器远程访问（`web-auth`） | 原生壳天然不具备，且当前 Electron 版也只绑 127.0.0.1 |
| 多标签页 / 浏览器通知 | 用原生窗口与系统通知替代 |
| 内置 Node / npm | 内核换官方独立二进制，无 npm 安装行为 |

### v1 完成的定义（DoD）

1. 附录 A 的 1:1 对照表全绿（标 `OUT` 的除外）；
2. Windows x64 安装包 ≤ 220MB，空机器双击可用（除模型 API Key 外零配置）；
3. 连续 7 天作为主力客户端使用无阻断性缺陷。

## 二、上游钉版本与解冻策略

v1 开发期间**锁死**，不追上游。

| 上游 | 钉死值 | 角色 |
|---|---|---|
| `agegr/pi-web` | `v0.8.9` / `2a6e53710f6409e0cceb3de839a62f8cdf3ca3ca` (2026-08-15) | **功能对照基线**，只读源码，不作运行时依赖；固定在 `vendor/upstream/pi-web-0.8.9/` |
| `earendil-works/pi` | `v0.84.2` / `914cf1472e715297caa30db4b9535d534a9eb718` | 运行时内核用官方独立二进制；源码参考固定在 `vendor/upstream/pi-0.84.2/` |
| `longbridge/gpui-component` | `000114aa` (2026-08-15) | UI 组件库 |
| `zed-industries/zed`（gpui / gpui_platform） | `cc053a4a` | 与上面那版 gpui-component 的 `Cargo.lock` 一致 |

**为什么必须钉**：近 60 天上游 `pi-web` 398 commit、`pi` 内核 1108 commit。移动靶做不了 1:1；GPUI 自身 pre-1.0，跟 main 分支会被 breaking change 打断节奏。

**解冻策略**（v1 交付之后，不在本文档范围内执行）：
- 先解 `pi` 内核（只有 RPC 协议这一个接触面，风险最小），跑通全部 T2 集成测试再合；
- 再解 gpui / gpui-component（一次一个，看 CHANGELOG 逐条评估）；
- `pi-web` 基线最后解 —— 它只是对照物，解冻等于"接受新的复刻目标"，应作为 v2 立项决策而非日常维护。
- 解冻时 diff 是**积压量不是增量**，预留独立的一轮工作，不要塞进功能轮次。

## 三、目标架构

```
┌──────────────────────────────────────────────┐
│  GPUI-Pi.exe   (Rust, 原生绘制)               │
│  ┌────────────┬────────────┬───────────────┐ │
│  │ crates/app │ crates/ui  │ crates/render │ │  ← 依赖 GPUI
│  └────────────┴────────────┴───────────────┘ │
│  ┌────────────────────┬─────────────────────┐│
│  │ crates/pi-rpc      │ crates/pi-data      ││  ← 纯逻辑，不依赖 GPUI
│  └────────────────────┴─────────────────────┘│
└───────┬──────────────────────────┬───────────┘
        │ JSONL over stdin/stdout  │ 直接读写文件
        ▼                          ▼
  vendor/pi/pi.exe            ~/.pi/agent/
  (--mode rpc, 一会话一进程)   sessions/ models.json
                              settings.json extensions/ skills/
```

### crate 划分（关键设计决策）

| crate | 依赖 GPUI | 职责 |
|---|---|---|
| `pi-rpc` | ❌ | 子进程生命周期、JSONL 分帧、39 个命令/事件的 serde 定义、请求-响应 id 关联、崩溃重启 |
| `pi-data` | ❌ | `~/.pi/agent/` 文件层：会话 JSONL 解析、`models.json`、`settings.json`、扩展/技能目录扫描、项目分组 |
| `pi-render` | ❌ | 消息 → 可渲染中间模型：Markdown 分块、ANSI 解析、diff 解析、工具调用卡片归类 |
| `ui` | ✅ | 基于 gpui-component 的应用级组件封装 |
| `app` | ✅ | 窗口、面板布局、状态编排、入口 |

> **三个纯逻辑 crate 不依赖 GPUI**：它们无需窗口、无需 GPU 即可 100% 单测，CI 跑得快、T2 集成测试可全自动，UI 层才需要真机目视。

### 仓库结构

```
GPUI-Pi/
├── crates/{app,ui,pi-rpc,pi-data,pi-render}/
├── vendor/pi/              # 官方 pi 二进制（构建输入，gitignored）
├── vendor/upstream/pi-0.84.2/ # 钉 tag + commit 的只读源码参考（gitignored）
├── vendor/upstream/pi-web-0.8.9/ # 钉 tag + commit 的功能对照基线（gitignored）
├── pins/pi-0.84.2.manifest # pi 源码逐文件 SHA256 + 大小基线（提交进 git）
├── pins/pi-web-0.8.9.manifest # pi-web 逐文件 SHA256 + 大小基线（提交进 git）
├── rounds/                 # 轮次级管理文档
│   ├── {README,TEMPLATE,BACKLOG}.md
│   └── round-NN/round-NN.md # 每轮独立目录与任务卡
├── scripts/{validate.*,fetch-pi.*,fetch-pi-source.*,fetch-pi-web.*,check-pins.*,check-pi-source-pin.*,check-pi-web-pin.*}
├── tests/fixtures/         # 真实会话 JSONL 脱敏快照
├── docs/
├── .github/workflows/ci.yml
├── CLAUDE.md / AGENTS.md   # 开发约定与编码红线（R0 产出）
└── ROUNDS.md               # 轮次进度表
```

### 会话与进程模型

- **一个活跃会话 = 一个 `pi --mode rpc` 子进程**（实测常驻 ~203MB）。这是相对 pi-web 的**内存回归**：pi-web 是单 Node 进程内 `Map<sessionId, AgentSessionWrapper>` 挂 N 个会话。
- 对策：只给**活跃会话**起进程，历史会话直接读 JSONL 渲染；会话关闭即杀进程；同时活跃进程数设上限（默认 3，可配）并在 UI 上显式提示。

## 五、已知技术缺口与对策

| # | 缺口 | 影响 | 对策 | 落在 |
|---|---|---|---|---|
| ① | RPC 0.84.2 **没有**工具启用/禁用命令（`getAllTools`/`setActiveToolsByName`） | Tools chip、工具预设切换 | 启动参数 `--tools` 定死；运行时切换 = 带新参数重启子进程 + resume | R10 |
| ② | RPC 没有 `reload` / `clear_queue` / `navigateTree` | `/reload`、清队列、树内导航 | `reload` 走重启子进程；`clear_queue` 客户端侧不入队；导航用 `get_tree` + `switch_session` 组合 | R13 |
| ③ | pi-web 在**进程内**注入 bash 扩展（`createProjectCommandBashExtension`）实现项目命令环境 | bash 工具的环境隔离行为不一致 | 复刻成一个 `.ts` 扩展，用 `pi -e <path>` 传入 | R15 |
| ④ | 钉死二进制 → **不能给 pi 打补丁** | ①②③ 只能客户端绕 | 已接受；若某项绕不过去，记入 v2 的"给上游提 RPC 命令 PR" | — |
| ⑤ | GPUI pre-1.0；中文 IME 走 IMM32 而非 TSF（详见下方核查） | 中文输入是刚需，可能一票否决 | **R1 风险 spike 设为门禁**，不过就停项 | R1 |
| ⑥ | 无内置 Python | `wiki-*` / `ppt-master` 失效 | v1 明确移出范围；技能由 pi-web-desktop 侧继续提供 | — |
| ⑦ | 流式 Markdown 每次 delta 全量重解析（gpui-component `TextView` 默认行为） | 长回复可能掉帧 | R1 实测；不达标则自己做"已定稿段落缓存 + 尾段增量"分块渲染 | R1 / R7 |

### 缺口⑤ 展开：GPUI 的 Windows 端是官方支持，不是社区支持

这条容易踩错判断，所以把核查结果留档。**证据取自我们钉死的那个 commit（`cc053a4a`）的源码本身**，不是二手说法。

| 核查项 | 结论 |
|---|---|
| crate 归属 | `crates/gpui_windows` 是 zed monorepo 的 in-tree 一等 crate，**12,120 行**，与 `gpui_linux`（15,070）、`gpui_macos`（12,503）同量级，不是薄适配层 |
| 官方 CI | `.github/workflows/run_tests.yml` 有 `clippy_windows` 与 `run_tests_windows`，跑在自建 32 vCPU Windows runner（`self-32vcpu-windows-2022`），且二者都在最终门禁 job 的 `needs` 里 —— 与 linux/mac 并列必过 |
| 发版流水线 | `release.yml` / `release_nightly.yml` / `run_bundling.yml` 均含 windows |
| gpui README | Windows 列为三平台之一：「no features are required. Windowing uses Win32 and text uses DirectWrite」 |
| 官方文档 | `zed.dev/docs/windows` 提供 stable 下载与 winget 安装，无 experimental / community / preview 字样；`docs/src/development/windows.md` 是正式构建指南 |

**历史来源**：2024–2025 年 Windows 端长期是「社区推动 + 官方不发包、只能自源码编译」，转折点是 Zed 1.0（发布页记 2026-04-29）三平台齐发。旧印象已过期。

**所以风险不在"非官方"，而在这三条**：

1. GPUI 自身 pre-1.0，README 明写 frequent breaking changes —— 已用提交进仓库的 `Cargo.lock` 对冲；
2. Windows 后端更年轻，新特性通常 macOS/Linux 先落地；
3. **IME 走 IMM32 而非 TSF**。钉死 commit 里的实现是完整的 —— `WM_IME_STARTCOMPOSITION` / `WM_IME_COMPOSITION` 消息处理、`ImmSetCompositionWindow` + `ImmSetCandidateWindow`（候选窗定位）、`ImmAssociateContextEx`（启停）、`ImmNotifyIME(NI_COMPOSITIONSTR, CPS_COMPLETE)`（提交组合串）—— 但 IMM32 路线在部分输入法上存在已知边角。

结论：**风险定性从「可能不成熟」修正为「实现完整，但 IMM32 路线需实测验证」。R1 门禁第 1 条照测不误**，不因为"官方支持"而放宽。

## 六、开发模式：`/loop` 强制规范

### 轮次任务卡

每轮建立独立目录 `rounds/round-NN/`，任务卡固定为 `rounds/round-NN/round-NN.md`；该轮的实测记录、阻塞报告、复盘等管理产出也放在此目录。`rounds/` 根目录只保留 `README.md`、`TEMPLATE.md`、`BACKLOG.md`。源码、脚本、fixture 与构建产物仍放标准工程目录，不复制进轮次目录。

任务卡结构固定：

```markdown
# Round NN — <标题>
## 目标            一句话，可证伪
## 前置            依赖哪些轮次已完成
## 交付物          文件级清单
## 验收            可执行命令 + 期望结果（T1/T2/T3 分级）
## 禁止            本轮明确不许碰的东西（防范围蔓延）
## 失败处理        连续 2 次 validation 不过 → 停下写 BLOCKED.md 并呼人
```

### loop 契约

1. **一轮 = 一个 `/loop` 任务**，允许内部多次迭代，直到 `scripts/validate.*` 全绿；
2. 每次迭代结束**必须**跑 validation，不许"看起来对了就下一步"；
3. 全绿后：一个 commit（message 说明 why）+ 更新 `ROUNDS.md` 进度表 + 在任务卡尾部追加 `## 本轮实测` 段落（数字、踩坑、偏离设计的地方）；
4. **禁止跨轮次改动**。发现前面轮次有问题 → 记进 `rounds/BACKLOG.md`，不当场改；
5. 连续 2 次 validation 失败 → 写 `rounds/round-NN/BLOCKED.md` 停下呼人，不许放宽验收标准自我通过。

### 验收分级

| 级别 | 含义 | 谁执行 |
|---|---|---|
| **T1** 静态 | `cargo fmt --check` / `clippy -D warnings` / `cargo test` / `cargo build --release` | AI 自动 |
| **T2** 集成 | 打**真实 pi 二进制**的黑盒测试（只用不烧 token 的命令：`get_state`/`get_commands`/`get_tree`/`new_session`/`set_thinking_level`）+ fixture 渲染快照 | AI 自动 |
| **T3** 目视 | UI 观感、中文 IME、流式流畅度、打包安装 | **人工** |

> T3 是唯一不能自动化的一档。轮次设计上**尽量把 T3 集中在少数几轮**（R1、R7、R17、R18），其余轮次做到 T1+T2 即可判定。

## 七、轮次拆解

共 19 轮，四个阶段。每轮结束仓库都必须"可编译、可运行、不倒退"。

### 阶段 A · 地基与门禁（R0–R3）

| 轮 | 目标 | 交付物 | 验收 | 执行方 |
|---|---|---|---|---|
| **R0** | 工程骨架 | 5 个 crate 的 workspace 空壳；`rust-toolchain.toml`（钉 1.97.1）；`Cargo.lock` 钉死 gpui `cc053a4a` / gpui-component `000114aa`；`scripts/validate.{sh,ps1}`；`scripts/fetch-pi.{sh,ps1}`（按平台拉 v0.84.2 二进制到 `vendor/pi/`）；`scripts/fetch-pi-source.{sh,ps1}` + `pins/pi-0.84.2.manifest`（tag + commit + 归档 SHA256 + 全量内容清单四重钉死，落到 `vendor/upstream/pi-0.84.2/`）；`scripts/fetch-pi-web.{sh,ps1}` + `pins/pi-web-0.8.9.manifest`（同样四重钉死，落到 `vendor/upstream/pi-web-0.8.9/`）；GitHub Actions；`CLAUDE.md` / `AGENTS.md`；`ROUNDS.md` | T1 全绿；CI 绿；二进制 `--version` 输出 `0.84.2`；两个参考目录的 marker 与 manifest 全量校验通过 | **130 Arch** |
| **R1** | ⚠️ **风险门禁 spike** | 一个 demo 窗口，只做四件事 | 见下方门禁清单，**四条全过才准进 R2** | Windows |
| **R2** | `pi-rpc` crate | 子进程管理（spawn/kill/崩溃重启）；JSONL 分帧（只按 `\n` 切、剥尾部 `\r`）；39 个命令/事件 serde 类型；请求-响应 id 关联；事件广播 | T2：起真实 pi 打完整命令矩阵；断电测试（中途 kill 子进程能自愈重启并 resume） | Windows |
| **R3** | `pi-data` crate | 会话 JSONL 解析（按 `session-format.md`）；`models.json` / `settings.json` / `trust.json` 读写；扩展目录扫描（含 `.disabled` 约定）；按项目分组 + worktree 归并 | T2：用真实 `~/.pi` 脱敏快照做 fixture 单测，覆盖 ≥ 20 个真实会话文件不 panic | Windows |

**R1 门禁清单（四条全过）**

1. 微软拼音 / 搜狗在多行输入框中：候选窗定位正确、组合期不丢字、`Enter` 只提交候选不误发消息；
2. 8000 token 长文本按 30ms/chunk 流式灌入 Markdown 视图，**帧率不低于 50fps**（用 `gpui-fps` 测）；
3. 跨 5 条消息框选复制，剪贴板内容格式正确；
4. 窗口冷启动到可交互 **< 1.5s**。

> 任一条不过 → 写 `rounds/round-01/BLOCKED.md` 停项汇报，不许降低标准继续。

## 八、开发平台与环境约定

**交付目标是 Windows x64。开发也在 Windows —— 除 R0 外全部轮次由 Windows 端执行。**

| 范围 | 执行方 |
|---|---|
| **R0**（工程骨架、CI、脚本、`CLAUDE.md`/`AGENTS.md`、`ROUNDS.md`） | 130 Arch |
| **R1–R18**（全部实现、测试、打包、验收） | **Windows** |
| CI | `windows-latest` **阻断**；`ubuntu-latest` 仅作静态兜底，**非阻断**（无人在 Linux 上开发，不让它挡合并） |

### 为什么不是分工偏好，而是技术结论

GPUI 的 Windows 后端依赖 DirectX 与 COM，链接走 MSVC —— **从 Linux 交叉编译 Windows 目标不可行**。任何在 Linux 上写的 UI 代码都必须到 Windows 上重新编译验证一次，双端并行只会制造两套未验证状态。加上中文 IME、流畅度、打包安装这三类 T3 验收本来就只有 Windows 是有效环境，把实现也放在 Windows 才能做到"写完即可验"。

### R0 在 130 上的前置

```bash
rustup update stable          # 当前 1.94.0 → 1.97.1
bash scripts/fetch-pi.sh      # 拉 pi-linux-x64 v0.84.2，验证 --version
```

R0 只产出骨架与脚本，不起窗口，因此**不需要 GPU/Vulkan**。（若日后要在 130 上临时跑一次 demo 窗口，需先 `sudo pacman -S vulkan-intel` —— 当前 `/usr/share/vulkan/icd.d/` 为空，`libvulkan` 装了但驱动 ICD 没装。）

### Windows 开发环境前置（R1 开始）

```powershell
# 1. MSVC 工具链：Visual Studio Build Tools + Windows SDK
# 2. rustup toolchain install 1.97.1-x86_64-pc-windows-msvc
# 3. .\scripts\fetch-pi.ps1        # 拉 pi-windows-x64 v0.84.2 到 vendor\pi\
# 4. .\scripts\fetch-pi-source.ps1 # 拉钉死源码到 vendor\upstream\pi-0.84.2\
# 5. 长路径：git config --global core.longpaths true
#            注册表 LongPathsEnabled = 1
```

源码参考目录以 `v0.84.2` 对应 commit `914cf1472e715297caa30db4b9535d534a9eb718` 为唯一身份；目录无 `.git`，后续升级必须创建新的版本目录，禁止覆盖。不得再从 `D:/Program Files/Pi Agent/resources/runtime-seed/` 等会被桌面应用自动更新的安装位置读取权威源码。

### 编码约定（写进 `CLAUDE.md`，每轮必守）

以 Windows 为第一目标，但**不写死平台假设** —— Linux 构建仍是 CI 的静态兜底，也是未来可能的发布目标。

| 项 | 约定 |
|---|---|
| 换行 | `.gitattributes` 强制 `* text=auto eol=lf`；Rust 源码一律 LF。判断"文件是否被改过"的哈希必须**忽略换行差异**（pi-web-desktop 踩过这个坑） |
| 路径 | 一律 `std::path::Path`，禁止手拼 `/` 或 `\`；长路径用 `\\?\` 前缀或 `dunce` 规范化 |
| 子进程终止 | 抽象成 `pi_rpc::Process::terminate()`：Windows `taskkill /T /PID`（不能只杀父进程，会留僵尸），非 Windows 走 `kill(-pgid)` |
| 文件替换 | Windows 上**正在被打开的文件不能删/改名** —— 所有原子替换走"写临时文件 + rename"，且 rename 前确保句柄已关 |
| 字体回退 | Windows 用微软雅黑 / Segoe UI，其他平台 Noto Sans CJK SC；字体族列表按平台条件编译，禁止硬编码单一字体 |
| 环境变量 | `HOME` 在 Windows 上是 `USERPROFILE`，统一走 `dirs` crate；`PI_CODING_AGENT_DIR` 必须支持 |
| 测试 fixture | 会话目录名带平台印记（`--C--Users-...` vs `--home-...`），fixture 存归一化后的形式，加载时按平台还原 |

### 协作流程

- 走 **worktree + PR**：R0 分支 `ArchLinuxClaude/round-00`，R1 起 `WinClaude/round-NN`；
- `main` 只接受 PR 合并，不直推；
- 每轮 PR 描述必须贴 validation 输出（T1/T2 的实际命令回显），不贴不审；
- 子代理做代码审查时，优先显式使用 **DeepSeek provider** 的 `deepseek/deepseek-v4-pro`；不得替换成 `variflight-ticket`、OpenRouter、V4 Flash 或其他型号。该模型不可用或启动失败时，不传 `model` 重试 reviewer，使其继承主会话模型；
- R1 之后 130 端只做**只读**工作（上游源码考古、协议对照、文档），不提交实现代码。
