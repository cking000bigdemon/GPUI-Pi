# GPUI-Pi 立项文档

> 状态：**待审计** · 创建 2026-08-16 · 作者 ArchLinuxClaude（130 Arch）

## 一、项目定位与边界

用 GPUI + gpui-component 写一个 **pi 编程智能体的原生桌面客户端**，1:1 复刻 pi-web 0.8.9 的能力，不使用 Electron、不打包 Node/Python/DeepSeek Harness。

这是**新仓库、新项目**，不是 pi-web-desktop 的重写分支。两者并行存在、共用 `~/.pi/agent/`：

| | pi-web-desktop（保留） | GPUI-Pi（本项目） |
|---|---|---|
| 定位 | 兜底 + DeepSeek Harness 入口 + 扩展/技能部署 | 日常 pi 客户端 |
| 演进 | 冻结在 `claude/dsh-integration` 状态，不再加 pi 侧功能 | 主线 |
| 卸载条件 | GPUI-Pi 达到 1:1 且稳定运行 1 个月后再议 | — |

### 明确不做（v1）

| 不做 | 理由 |
|---|---|
| 内置 Python | 体积（340MB）；连带 `ppt-master`、`wiki-*`、`okf-visualizer` **全部移出 v1 范围** |
| 内置技能部署（`skills-seed`） | 技能住在 `~/.pi/agent/skills/`，由 pi-web-desktop 负责铺；GPUI-Pi 只消费不部署 |
| DeepSeek Harness 第二运行时 | 留在 pi-web-desktop |
| Mermaid 渲染 | 源码直出为代码块。**连带收益：不需要 WebView，不依赖 WebView2 Runtime** |
| PWA / 移动端布局 / 浏览器远程访问（`web-auth`） | 原生壳天然不具备，且当前 Electron 版也只绑 127.0.0.1 |
| 多标签页 / 浏览器通知 | 用原生窗口与系统通知替代 |
| 内置 Node / npm | 内核换官方独立二进制，无 npm 安装行为 |

### v1 完成的定义（DoD）

1. 附录 A 的 1:1 对照表全绿（标 `OUT` 的除外）；
2. Windows x64 安装包 ≤ 220MB，空机器双击可用（除模型 API Key 外零配置）；
3. 连续 7 天作为主力客户端使用无阻断性缺陷。

## 二、上游钉版本与解冻策略

v1 开发期间**锁死**，不追上游。

| 上游 | 钉死值 | 角色 |
|---|---|---|
| `agegr/pi-web` | `v0.8.9` / `2a6e5371` (2026-08-15) | **功能对照基线**，只读源码，不作运行时依赖 |
| `earendil-works/pi` | `v0.84.2` | 运行时内核，用官方发布的独立二进制 |
| `longbridge/gpui-component` | `000114aa` (2026-08-15) | UI 组件库 |
| `zed-industries/zed`（gpui / gpui_platform） | `cc053a4a` | 与上面那版 gpui-component 的 `Cargo.lock` 一致 |

**为什么必须钉**：近 60 天上游 `pi-web` 398 commit、`pi` 内核 1108 commit。移动靶做不了 1:1；GPUI 自身 pre-1.0，跟 main 分支会被 breaking change 打断节奏。

**解冻策略**（v1 交付之后，不在本文档范围内执行）：
- 先解 `pi` 内核（只有 RPC 协议这一个接触面，风险最小），跑通全部 T2 集成测试再合；
- 再解 gpui / gpui-component（一次一个，看 CHANGELOG 逐条评估）；
- `pi-web` 基线最后解 —— 它只是对照物，解冻等于"接受新的复刻目标"，应作为 v2 立项决策而非日常维护。
- 解冻时 diff 是**积压量不是增量**，预留独立的一轮工作，不要塞进功能轮次。

## 三、目标架构

```
┌──────────────────────────────────────────────┐
│  GPUI-Pi.exe   (Rust, 原生绘制)               │
│  ┌────────────┬────────────┬───────────────┐ │
│  │ crates/app │ crates/ui  │ crates/render │ │  ← 依赖 GPUI
│  └────────────┴────────────┴───────────────┘ │
│  ┌────────────────────┬─────────────────────┐│
│  │ crates/pi-rpc      │ crates/pi-data      ││  ← 纯逻辑，不依赖 GPUI
│  └────────────────────┴─────────────────────┘│
└───────┬──────────────────────────┬───────────┘
        │ JSONL over stdin/stdout  │ 直接读写文件
        ▼                          ▼
  vendor/pi/pi.exe            ~/.pi/agent/
  (--mode rpc, 一会话一进程)   sessions/ models.json
                              settings.json extensions/ skills/
```

### crate 划分（关键设计决策）

| crate | 依赖 GPUI | 职责 |
|---|---|---|
| `pi-rpc` | ❌ | 子进程生命周期、JSONL 分帧、39 个命令/事件的 serde 定义、请求-响应 id 关联、崩溃重启 |
| `pi-data` | ❌ | `~/.pi/agent/` 文件层：会话 JSONL 解析、`models.json`、`settings.json`、扩展/技能目录扫描、项目分组 |
| `pi-render` | ❌ | 消息 → 可渲染中间模型：Markdown 分块、ANSI 解析、diff 解析、工具调用卡片归类 |
| `ui` | ✅ | 基于 gpui-component 的应用级组件封装 |
| `app` | ✅ | 窗口、面板布局、状态编排、入口 |

> **三个纯逻辑 crate 不依赖 GPUI，是双端分工的技术基础**：它们在无显示器的 Linux 上可以 100% 单测 + CI 覆盖，UI 层才需要真机目视。

### 仓库结构

```
GPUI-Pi/
├── crates/{app,ui,pi-rpc,pi-data,pi-render}/
├── vendor/pi/              # 官方 pi 二进制（构建输入，gitignored）
├── rounds/round-NN.md      # 每轮任务卡
├── scripts/{validate.sh,validate.ps1,fetch-pi.sh,fetch-pi.ps1}
├── tests/fixtures/         # 真实会话 JSONL 脱敏快照
├── docs/
├── .github/workflows/ci.yml
├── CLAUDE.md / AGENTS.md   # 双端开发约定（R0 产出）
└── ROUNDS.md               # 轮次进度表
```

### 会话与进程模型

- **一个活跃会话 = 一个 `pi --mode rpc` 子进程**（实测常驻 ~203MB）。这是相对 pi-web 的**内存回归**：pi-web 是单 Node 进程内 `Map<sessionId, AgentSessionWrapper>` 挂 N 个会话。
- 对策：只给**活跃会话**起进程，历史会话直接读 JSONL 渲染；会话关闭即杀进程；同时活跃进程数设上限（默认 3，可配）并在 UI 上显式提示。

## 五、已知技术缺口与对策

| # | 缺口 | 影响 | 对策 | 落在 |
|---|---|---|---|---|
| ① | RPC 0.84.2 **没有**工具启用/禁用命令（`getAllTools`/`setActiveToolsByName`） | Tools chip、工具预设切换 | 启动参数 `--tools` 定死；运行时切换 = 带新参数重启子进程 + resume | R9 |

| ④ | 钉死二进制 → **不能给 pi 打补丁** | ①②③ 只能客户端绕 | 已接受；若某项绕不过去，记入 v2 的"给上游提 RPC 命令 PR" | — |
| ⑤ | GPUI pre-1.0；Windows IME 今年 8 月仍在修 bug | 中文输入是刚需，可能一票否决 | **R1 风险 spike 设为门禁**，不过就停项 | R1 |
| ⑥ | 无内置 Python | `wiki-*` / `ppt-master` 失效 | v1 明确移出范围；技能由 pi-web-desktop 侧继续提供 | — |
| ⑦ | 流式 Markdown 每次 delta 全量重解析（gpui-component `TextView` 默认行为） | 长回复可能掉帧 | R1 实测；不达标则自己做"已定稿段落缓存 + 尾段增量"分块渲染 | R1 / R7 |

## 六、开发模式：`/loop` 强制规范

### 轮次任务卡

每轮一个 `rounds/round-NN.md`，结构固定：

```markdown
# Round NN — <标题>
## 目标            一句话，可证伪
## 前置            依赖哪些轮次已完成
## 交付物          文件级清单
## 验收            可执行命令 + 期望结果（T1/T2/T3 分级）
## 禁止            本轮明确不许碰的东西（防范围蔓延）
## 失败处理        连续 2 次 validation 不过 → 停下写 BLOCKED.md 并呼人
```

### loop 契约

1. **一轮 = 一个 `/loop` 任务**，允许内部多次迭代，直到 `scripts/validate.*` 全绿；
2. 每次迭代结束**必须**跑 validation，不许"看起来对了就下一步"；
3. 全绿后：一个 commit（message 说明 why）+ 更新 `ROUNDS.md` 进度表 + 在任务卡尾部追加 `## 本轮实测` 段落（数字、踩坑、偏离设计的地方）；
4. **禁止跨轮次改动**。发现前面轮次有问题 → 记进 `rounds/BACKLOG.md`，不当场改；
5. 连续 2 次 validation 失败 → 写 `rounds/BLOCKED-NN.md` 停下呼人，不许放宽验收标准自我通过。

### 验收分级

| 级别 | 含义 | 谁执行 | 环境 |
|---|---|---|---|
| **T1** 静态 | `cargo fmt --check` / `clippy -D warnings` / `cargo test` / `cargo build --release` | AI 自动 | 双端均可 |
| **T2** 集成 | 打**真实 pi 二进制**的黑盒测试（只用不烧 token 的命令：`get_state`/`get_commands`/`get_tree`/`new_session`/`set_thinking_level`）+ fixture 渲染快照 | AI 自动 | 双端均可（Linux 用 `pi-linux-x64`） |
| **T3** 目视 | UI 观感、中文 IME、流式流畅度、打包安装 | **人工** | 优先 Windows；Linux 有屏会话可预检 |

> T3 是唯一不能自动化的一档。轮次设计上**尽量把 T3 集中在少数几轮**（R1、R7、R16、R17），其余轮次做到 T1+T2 即可判定。

## 七、轮次拆解

共 18 轮，四个阶段。每轮结束仓库都必须"可编译、可运行、不倒退"。

### 阶段 A · 地基与门禁（R0–R3）

| 轮 | 目标 | 交付物 | 验收 | 平台 |
|---|---|---|---|---|
| **R0** | 工程骨架 | 5 个 crate 的 workspace 空壳；`rust-toolchain.toml`（钉 1.97.1）；`Cargo.lock` 钉死 gpui `cc053a4a` / gpui-component `000114aa`；`scripts/validate.{sh,ps1}`；`scripts/fetch-pi.{sh,ps1}`（按平台拉 v0.84.2 二进制到 `vendor/pi/`）；GitHub Actions（ubuntu + windows 双矩阵）；`CLAUDE.md` / `AGENTS.md`；`ROUNDS.md` | T1 全绿；CI 双平台绿；`fetch-pi` 拉下来的二进制 `--version` 输出 `0.84.2` | 双端 |
| **R1** | ⚠️ **风险门禁 spike** | 一个 demo 窗口，只做四件事 | 见下方门禁清单，**四条全过才准进 R2** | **必须 Windows 实测** |
| **R2** | `pi-rpc` crate | 子进程管理（spawn/kill/崩溃重启）；JSONL 分帧（只按 `\n` 切、剥尾部 `\r`）；39 个命令/事件 serde 类型；请求-响应 id 关联；事件广播 | T2：起真实 pi 打完整命令矩阵；断电测试（中途 kill 子进程能自愈重启并 resume） | 双端 |
| **R3** | `pi-data` crate | 会话 JSONL 解析（按 `session-format.md`）；`models.json` / `settings.json` / `trust.json` 读写；扩展目录扫描（含 `.disabled` 约定）；按项目分组 + worktree 归并 | T2：用真实 `~/.pi` 脱敏快照做 fixture 单测，覆盖 ≥ 20 个真实会话文件不 panic | 双端 |

**R1 门禁清单（四条全过）**

1. 微软拼音 / 搜狗在多行输入框中：候选窗定位正确、组合期不丢字、`Enter` 只提交候选不误发消息；
2. 8000 token 长文本按 30ms/chunk 流式灌入 Markdown 视图，**帧率不低于 50fps**（用 `gpui-fps` 测）；
3. 跨 5 条消息框选复制，剪贴板内容格式正确；
4. 窗口冷启动到可交互 **< 1.5s**。

> 任一条不过 → 写 `rounds/BLOCKED-01.md` 停项汇报，不许降低标准继续。

## 八、Windows / Linux 双端开发差异

**交付目标是 Windows x64**；Linux（130 Arch）是开发与 CI 的一半，不是交付平台。

### 能力矩阵

| 维度 | Linux（130 Arch） | Windows |
|---|---|---|
| 能否跑 GPUI 应用 | ✅ 可以 —— Wayland 会话 + Intel Raptor-Lake UHD。**前置：`sudo pacman -S vulkan-intel`**（当前 `/usr/share/vulkan/icd.d/` 为空，只有 `libvulkan` 装了驱动没装） | ✅ 原生（DirectX 后端） |
| 渲染后端 | Blade / Vulkan | DirectX |
| Rust 工具链 | 当前 1.94.0，**需 `rustup update` 到 1.97.1** | 需 MSVC toolchain（Build Tools + Windows SDK） |
| 交叉编译到 Windows | ❌ **不可行** —— GPUI 的 Windows 后端依赖 DirectX/COM 与 MSVC 链接器 | — |
| pi 二进制 | `pi-linux-x64.tar.gz`（解包 110MB） | `pi-windows-x64.zip`（解包约 110MB） |
| 中文 IME 验证 | 只能验 fcitx5/ibus，**不等价** | ✅ 微软拼音 / 搜狗，**唯一有效验证环境** |
| 打包验证 | AppImage/tar | NSIS/MSI，**必须在此做** |

### 分工建议

| 归 Linux Claude（130） | 归 Windows Claude |
|---|---|
| `pi-rpc` / `pi-data` / `pi-render` 三个纯逻辑 crate 的全部实现与单测 | UI 层目视、IME、流畅度（全部 T3） |
| fixture 制作、协议对照、上游源码考古（pi-web 0.8.9 逐文件读） | 打包、安装、空机器冒烟 |
| CI 配置、脚本、文档 | Windows 特有 bug 的定位与修复 |
| 能跑 T1+T2 的所有轮次 | R1 / R7 / R8 / R16 / R17 的把关 |

### 编码差异清单（写进 `CLAUDE.md`，每轮必守）

| 项 | 约定 |
|---|---|
| 换行 | 仓库 `.gitattributes` 强制 `* text=auto eol=lf`；Rust 源码一律 LF。判断"文件是否被改过"的哈希必须**忽略换行差异**（pi-web-desktop 踩过这个坑） |
| 路径 | 一律 `std::path::Path`，禁止手拼 `/` 或 `\`；Windows 长路径用 `\\?\` 前缀或 `dunce` 规范化 |
| 子进程终止 | 抽象成 `pi_rpc::Process::terminate()`：Linux `kill(-pgid)`，Windows `taskkill /T /PID`（不能只杀父进程，会留僵尸） |
| 文件替换 | Windows 上**正在被打开的文件不能删/改名** —— 所有原子替换走"写临时文件 + rename"，且 rename 前确保句柄已关 |
| 字体回退 | Linux 用 Noto Sans CJK SC，Windows 用微软雅黑 / Segoe UI；字体族列表按平台条件编译，禁止硬编码单一字体 |
| 环境变量 | `PI_CODING_AGENT_DIR` 双端都要支持；`HOME` 在 Windows 上用 `USERPROFILE`，统一走 `dirs` crate |
| 测试 fixture | 会话路径含平台差异（`--home-chenkun-...` vs `--C--Users-...`），fixture 要分平台或做归一化 |
| CI | `.github/workflows/ci.yml` 双矩阵 `ubuntu-latest` + `windows-latest`，两边都必须绿才允许合并 |

### 协作流程

- 两端都走 **worktree + PR**，分支前缀 `ArchLinuxClaude/round-NN` 与 `WinClaude/round-NN`；
- `main` 只接受 PR 合并，不直推；
